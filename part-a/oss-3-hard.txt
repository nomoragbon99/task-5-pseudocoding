```javascript
function parseServerFirstMessage(serverFirstMessage, clientNonce) {
  var dict = {}
  var parts = serverFirstMessage.split(',')
  for (var i = 0; i < parts.length; i++) {
    var part = parts[i]
    var equalsIndex = part.indexOf('=')
    if (equalsIndex !== -1) {
      dict[part.substring(0, equalsIndex)] = part.substring(equalsIndex + 1)
    }
  }

  if (!dict.r || !dict.r.startsWith(clientNonce)) {
    throw new Error('Server nonce does not start with client nonce')
  }

  if (!dict.s) {
    throw new Error('Server salt is missing')
  }

  var iterations = parseInt(dict.i, 10)
  if (!iterations || iterations <= 0 || isNaN(iterations)) {
    throw new Error('Invalid server iteration count: ' + dict.i)
  }

  return {
    nonce: dict.r,
    salt: Buffer.from(dict.s, 'base64'),
    iteration: iterations
  }
}
```

--------------------------------------------------------------------------------
PSEUDOCODE STANDARD HEADER
--------------------------------------------------------------------------------

FUNCTION parseServerFirstMessage
INPUTS:
  - serverFirstMessage: String, the raw comma-separated SASL SCRAM-SHA-256 payload received from the PostgreSQL server
  - clientNonce: String, the unpredictable cryptographic random nonce generated by the client during initial handshake
OUTPUT:
  - parsedParameters: Map containing:
      * nonce: String, the combined client-server nonce
      * salt: Binary Buffer, decoded binary salt bytes for PBKDF2 key derivation
      * iteration: Integer, positive iteration count for PBKDF2 hashing
SIDE EFFECTS:
  - NONE
FAILS WHEN:
  - serverFirstMessage is not text or is empty
  - clientNonce is not text or is empty
  - Combined server nonce ("r") is absent or does not start with clientNonce (replay/man-in-the-middle attack)
  - Salt parameter ("s") is absent or not valid base64
  - Iteration parameter ("i") is absent, non-numeric, or less than or equal to 0

--------------------------------------------------------------------------------
PSEUDOCODE BODY
--------------------------------------------------------------------------------

1. Validate the incoming message and client nonce parameters.
   IF serverFirstMessage is not text OR clientNonce is not text OR clientNonce is empty THEN
     RAISE ERROR "Invalid input arguments for SCRAM message parsing"
   OTHERWISE continue.

2. Initialize an empty key-value map named attributeDictionary.

3. Split serverFirstMessage by the comma delimiter "," into a list of attribute tokens named tokenList.

4. Parse each attribute token into a key and value pair.
   FOR EACH token IN tokenList:
     Find the first occurrence position of the equals sign "=" within token, storing it as splitIndex.
     IF splitIndex is found THEN
       Extract the substring of token from index 0 up to splitIndex, naming it attributeKey
       Extract the substring of token from splitIndex plus 1 to the end, naming it attributeValue
       WRITE attributeDictionary with attributeKey mapped to attributeValue
     OTHERWISE continue.
   END FOR

5. Verify that the combined server nonce is present in attributeDictionary under key "r".
   IF attributeDictionary does NOT contain key "r" THEN
     RAISE ERROR "Server nonce does not start with client nonce"
   OTHERWISE continue.

6. Retrieve the server nonce value from attributeDictionary, naming it serverNonce.

7. Ensure that serverNonce begins with the exact clientNonce previously issued by the client.
   IF serverNonce does NOT start with clientNonce THEN
     RAISE ERROR "Server nonce does not start with client nonce"
   OTHERWISE continue.

8. Verify that the cryptographic salt parameter is present in attributeDictionary under key "s".
   IF attributeDictionary does NOT contain key "s" OR attributeDictionary["s"] is empty THEN
     RAISE ERROR "Server salt is missing"
   OTHERWISE continue.

9. Decode the base64-encoded salt string from attributeDictionary["s"] into raw binary bytes.
   CALL binary buffer decoding from base64 (may fail), storing the resulting bytes as decodedSalt.

10. Parse the iteration count string located in attributeDictionary under key "i" as a base-10 integer.
    Store the parsed integer as parsedIterations.

11. Validate that parsedIterations is a valid positive whole number.
    IF parsedIterations is not a valid number OR parsedIterations is less than or equal to 0 THEN
      RAISE ERROR "Invalid server iteration count: " combined with the raw value from attributeDictionary["i"]
    OTHERWISE continue.

12. Construct the parsed result object containing:
    - nonce set to serverNonce
    - salt set to decodedSalt
    - iteration set to parsedIterations

13. RETURN the constructed result object.

AI COMPARISON & DISCREPANCY ANALYSIS
--------------------------------------------------------------------------------

1. AI Explanation Claim:
   When asked how to parse a SCRAM server-first-message, AI code assistants almost invariably
   produce a rigid regular expression:
   `const match = serverFirstMessage.match(/^r=([^,]+),s=([^,]+),i=(\d+)$/);`
   The AI asserts that SCRAM messages always follow this strict, exact sequence.

2. Actual Source Code Reality:
   The actual `node-postgres` codebase splits by comma and stores all key-value pairs in a
   dictionary map:
   `var parts = serverFirstMessage.split(',')`
   `for (...) { dict[part.substring(0, equalsIndex)] = part.substring(equalsIndex + 1); }`
   It extracts attributes by key lookup (`dict.r`, `dict.s`, `dict.i`) regardless of their order
   in the incoming packet, and silently ignores unexpected keys.

3. Who Was Correct and Why:
   THE LIBRARY CODE IS CORRECT; THE AI'S REGEX IS BRITTLE AND VIOLATES RFC 5802.
   - RFC 5802 Section 5.1 Specification: The SCRAM standard explicitly specifies that SASL
     attributes can be extended by future protocol revisions (such as channel-binding indicator
     flags `c=`, mandatory extensions `m=`, or server error attributes `e=`). Furthermore, the
     server is permitted to emit attributes in arbitrary order.
   - Failure of AI regex: If a PostgreSQL server sends attributes in the order `i=...,s=...,r=...`
     or includes an extension tag `m=...`, the AI regex completely fails to match (`null`),
     causing authentication crashes and connection drops in production.
   - Conclusion: The open-source `node-postgres` implementation correctly decouples attribute
     ordering from schema validation by building an intermediate dictionary, maintaining full
     compliance with Internet security standards.
